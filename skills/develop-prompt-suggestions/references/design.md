# 设计理由与真实数据流

这套设计优先保留用户真实意图、隔离辅助推理，并复用SDK已有的模型与传输能力。它不是另一个会执行任务的Agent，也不是自动维护用户画像的记忆服务。

## 独立预测，而不是接着主助手往下回答

主助手负责完成任务，预测器负责猜用户下一句。两者的目标、系统说明、推理档和输出语义不同。让它们共用主响应链，会把“预测出的用户话”混进真实聊天，或者扰动主请求前缀。

因此使用`<主会话ID>:prompt-suggestions`作为预测专属身份；认证、模型目录和HTTP/SSE/WebSocket仍复用Pi SDK。预测不声明可执行工具；返回工具调用也不会执行，候选为null。主系统规则和主助手隐藏推理不转发，图片只以`[image]`表示，不是视觉识别功能。

依据：`plugin/core.mjs`的`supportsSuggestion`、`visibleText`、`candidate`、`generateSuggestion`。

## 为什么压缩后清旧工具，而不直接拿摘要或截最近几条

工具材料常常比人与助手的交流大得多：文件正文、日志、搜索结果会让一次预测越来越贵，甚至超出窗口。反过来，用户较早说过的目标、约束、决定及助手给出的承诺，可能正是预测下一句所需的依据。简单截最近N条会同时丢掉这些内容；只用主会话摘要，会把模型的压缩选择当成用户原话。

当前取舍是：

1. **未压缩**：沿用主模型实际请求快照中的可见用户／助手／工具文字，并补本轮最后的助手回复。
2. **已经压缩**：沿当前原生分支找到最近的`compaction`；边界前只提取用户／助手可见文本，删除助手中的工具调用、纯工具调用消息和工具结果。
3. **边界后**：采用SDK带来源的有效投影，新增工具结果仍进入预测，保留宿主已有的截断或引用语义。
4. **下次压缩**：再次清理新边界前的旧工具。记录`compactionId`，边界改变就重建预测链。

这不是“保留整个会话全部数据”，也不是“压缩后不允许工具进入”。主会话近期保留区里已经位于压缩边界之前的工具，仍算旧工具，不应再次拼入。主摘要不替代保留的旧原话。

这样得到的是针对预测的证据投影；它不修改主会话、不会撤销主会话压缩，也没有额外摘要模型。当前原始分支确实存在旧原话时才能保留；若其他宿主已彻底删除原件，不能从摘要假造逐字原文。

依据：`buildCompactedSuggestionContext`；测试`compaction.test.mjs`及`editor.test.mjs`。

## 为什么用持久线程

每轮都重新整理、改写或总结历史，会破坏稳定前缀，还使重启后的行为难以恢复。持久线程把“已经交给预测器的真实证据”与“新增证据”区分开，正常时只在末尾追加，进程重启也能沿检查点恢复。

续接条件实际比较：配置指纹一致、压缩边界一致、旧证据哈希是当前证据哈希的精确前缀。证据完全没变就复用上一次候选，避免重复调用。分支或原文改写、模型/API/baseUrl、推理档、偏好或固定提示改变，都会重建。

### 两种持久化路径

| 通道 | 线程保存在哪 | 后续请求 |
| --- | --- | --- |
| xAI/OpenAI的`openai-responses` | 服务端`store:true`；本地保存响应ID和证据指纹，不另存全文 | 插件设置`previous_response_id`，发送新增证据和预测请求 |
| `openai-codex-responses` | `store:false`；本地保存完整预测输入、输出及该线程自身签名 | 交给SDK完整历史；同一有效WebSocket由SDK转成连接内delta，重连先重放，再恢复增量 |
| 其余已支持API | 不走上述持久检查点机制 | 独立全量请求 |

Codex不能因为想持久化就改为`store:true`；当前通道要求false，也不能把旧连接的响应ID直接拿到新连接继续用。插件不重写SDK的WebSocket传输。

服务端明确说旧响应不存在，或旧预测链超窗时，插件只用当前完整有效证据重建一次。若当前证据本身仍超窗，返回失败，不暗中裁掉材料。普通网络错误不触发插件级重发；SDK自身恢复是另一层。

依据：`generateSuggestion`、`threads.mjs`、`persistent.test.mjs`和`codex.test.mjs`。

## 它的预测和我们的真实输出如何进入下一次

预测线程的结构是：

```text
system：固定预测说明
user：{kind:user_preference_reference, preferences:人类原文}
user：{kind:conversation_evidence, role:user, text:真实用户话}
user：{kind:conversation_evidence, role:assistant, text:主助手真实回复}
user：{kind:prediction_request, revision:当前叶节点, instruction:预测下一句}
assistant：预测器自己的候选P1
user：{kind:conversation_evidence, role:user, text:用户实际发送的U2}
user：{kind:conversation_evidence, role:assistant, text:主助手实际回复A2}
user：{kind:prediction_request, revision:新叶节点, instruction:预测下一句}
assistant：新的候选P2
```

外层`user`是给预测器递交证据，内部`role`和`sourceIndex`标记原发言角色及顺序。预测器自身的旧输出保留为assistant，以稳定已有线程前缀；固定说明明确它只是预测，不是用户真的说过的话。

猜错时追加真实发言，不改写旧猜测。猜对且用户实际发送时，同一句可能出现两次：一次作为猜测，一次作为真实证据；语义不同。候选只有经人接受并发送才进入主聊天。主压缩或配置改变导致重建时，旧预测链的猜测不会作为真实证据带回。

固定说明和偏好放前面，变化的revision放预测请求尾部，避免每轮在开头插入变化字段。

## 三种“缓存”分开理解

- **本地检查点**解决进程重启后的恢复，文件存在不代表网络连接仍在。
- **连接内续接**减少上传历史；本地`lastRequest.mode=append`只表示本地历史追加，线上是否delta由SDK判断。
- **服务端token缓存**减少相同前缀的计算；要看实际usage.cacheRead，增量发送不表示历史不计费，全量重放也不表示零缓存。

断开活跃Codex预测连接通常会失去该连接内的续接状态，但不删除上一次成功的本地检查点。下一次可重放已成功历史；服务端是否命中前缀缓存以返回用量为准，不从本地文件推断缓存寿命。

## 为什么允许人直接调偏好

相同对话可能接“先解释为什么”，也可能接“直接做完”。这些个人协作倾向不一定能从眼前一轮判断。由人编辑偏好能补充预测依据，独立选模型／推理档则允许权衡速度、内容和额外额度，而不改变主聊天模型。

偏好是可选参考，不是固定台词、人格模仿规则或主助手系统指令。保存时保留原字符、空格和换行，允许清空；没有自动提炼、自动画像或后台改写。源码的四条V1仅是初始参考。修改运行偏好会改变配置指纹，使下一次预测用新偏好重建，而不是续接旧偏好的链。

配置位置、手改与导入方法见同目录`configuration.md`；实现为`preferences.mjs`、`settings.mjs`与`evidenceMessages`。

## 两分钟预算为何这样用

原来20秒总截止会连正常推理、等锁和SDK重试一起截掉。1.3.1采用用户接受的120000ms后台资源预算，并保留新一轮、配置／会话变化、关闭等失效取消。它不是证明请求故障的时间线，也不保证一定生成完。

不增加第二层重试、动态预算算法或调度队列。迟到结果不显示、不覆盖旧检查点。结束日志区分成功、空候选、错误及取消；取消原因有`budget_exhausted`、`no_longer_needed`。已知用量可记录，未知为null；取消不能撤销服务端已消耗的额度。
